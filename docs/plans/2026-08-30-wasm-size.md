# WASM size: where the bytes go, and the lite build

**Date:** 2026-08-30 (shipped sizes updated to the v0.4.2 branch point,
which added sidecar attachment and the embedded sparse vocabulary)
**Branch:** `feat/wasm-lite` (based on 0.4.1)
**Tooling:** Rust 1.96.0, `wasm-pack` 0.14, `twiggy` 0.7, `brotli -q 11`, `gzip -9`, `opt-level = s` (what `widget/build.sh` uses).

## Why

Every visitor who opens the search downloaded `dist/eddie.wasm` (3.49 MB raw,
711 KB brotli), although the CPU dense lane that needs candle is opt-in behind
a consent click and a 134 MB model download. The module also carried the
`tokenizers` crate (with its regex engines) only to WordPiece the query for the
sparse arm.

## Method

1. `cargo build --release --target wasm32-unknown-unknown --lib` with
   `CARGO_PROFILE_RELEASE_STRIP=none` so the name section survives, then
   `twiggy top --format json` and a script that folds the demangled function
   names into crates (`<T as Trait>::f` and `drop_in_place<T>` go to `T`'s
   crate). This is the module *before* `wasm-bindgen` runs: it still carries
   the `__wasm_bindgen_unstable` section and the `describe` stubs that
   `wasm-bindgen` strips, so the per-crate numbers are relative to each other,
   not to the shipped file.
2. Shipped sizes come from `scripts/build-wasm-variants.sh`, which runs
   `wasm-pack build --release` for both variants and both targets and prints
   raw / gzip / brotli bytes.

Reading the full column: candle + gemm + half + safetensors + rand (the dense
lane) is 868 KB of functions; regex + fancy-regex + tokenizers (the query
tokenizer) is 808 KB; std/serde bloat that those pull in accounts for most of
the remaining difference. The `.rodata` segment shrinks from 760 KB to 201 KB:
tokenizers' Unicode tables and regex's Unicode classes are gone, brotli's
122 KB static dictionary and Eddie's own 20 KB of WordPiece Unicode tables
(`src/wordpiece_tables.rs`) remain.

The `serde + serde_json` column is worth a note: 101 KB of the lite build is
JSON (manifest, `meta`, `qa`, `claims` sections and every result the JS side
reads). It is the largest remaining crate after std, and it was the obvious
next target -- until it was measured. See below.

## serde_json: measured, and left alone (2026-09-01)

Pass 2 was to cut `serde_json` out of the lite module if doing so saved at
least 20 KB brotli without changing the on-disk JSON manifest. Two
measurements, both on the lite `--no-default-features` build at
`opt-level=s`:

**Where the 101 KB actually sits.** Folding the twiggy rows by direction
rather than by crate:

| | function bytes |
|---|---:|
| deserialization (`serde_json::de`, `read`, `Value`, `ContentDeserializer`, every derived `Deserialize`) | 106,046 |
| serialization (`serde_json::ser` and every derived `Serialize`) | 13,558 |
| `ryu`, `itoa` and the rest of serde | 10,484 |

So the JS-facing side -- `serde_json::to_string` for search results,
capabilities and manifests -- is 13.5 KB and not worth touching. The weight
is in reading, and most of it is generic machinery (`deserialize_struct`
instantiations, escape and number parsing, `Value`) rather than per-struct
derived code: the seven largest `deserialize_struct` monomorphizations alone
are 34.6 KB.

**What removing the JSON payload sections would buy.** Building the lite
module with the `meta`, `qa` and `claims` sections' `serde_json::from_slice`
calls stubbed out under a temporary `--cfg`, and diffing against the same
build without it:

| lite module | raw | brotli |
|---|---:|---:|
| as shipped | 1,133,538 | 257,232 |
| with the three JSON sections not parsed | 1,114,174 | 254,216 |
| **difference** | **19,364** | **3,016** |

3 KB brotli, against a 20 KB bar. The reason is that the manifest is JSON
too, so the deserializer, the reader, the escape handling and `Value` stay
in the module no matter what the payload sections look like; only the three
derived `Deserialize` impls and their instantiations go. Even removing
*every* deserializer (106 KB of functions, so roughly 16 KB brotli at the
ratio the probe measured) would not clear the bar, and it would cost a
binary manifest -- unreadable by `eddie stats`, a format break for every
tool that reads an index, and a v6 bump.

Decision: keep `serde_json`. The next real cut in the lite module is
`std`/`core` (163 KB) or the 122 KB brotli dictionary, neither of which is
worth what it would cost.

## Shipped sizes (after `wasm-bindgen`, `opt-level=s`, no `wasm-opt`)

Built by `scripts/build-wasm-variants.sh` (which also tries `wasm-opt -Oz`
and keeps it only when the brotli size drops, like `widget/build.sh`; on
both variants `-Oz` grew the brotli output, 193,730 → 200,234 for lite and
725,633 → 777,556 for dense, so it was skipped).

The lite module is 3.66× smaller than the dense one after brotli (195 KB vs
715 KB) and loads for every visitor; the dense module is fetched only after
a visitor consents to the CPU lane, at which point it is a rounding error
next to the model weights (67 MB as bundled f16, 134 MB from HuggingFace).

## Brotli decision

Measured by building the lite module with the brotli compressor/decompressor
stubbed out (`bail!`) under a temporary `--cfg` and diffing against the normal
lite build (pre-`wasm-bindgen`, stripped, `opt-level=s`):

| lite module | raw | gzip | brotli |
|---|---:|---:|---:|
| with brotli | 1,099,301 | 349,044 | 250,402 |
| without brotli | 844,004 | 243,436 | 181,224 |
| **brotli's share** | **255,297** | **105,608** | **69,178** |

The share is 69 KB brotli-compressed (38 KB of decompressor code plus the
122 KB static dictionary, which compresses to about 30 KB). That is under the
120 KB line agreed for this work, so the container keeps brotli as its only
payload compression and no `--payload-compression gzip|none` option was
added. For reference, the site index payload (331 chunks) is 1.10 MB
brotli-compressed; gzip of the same payload would be roughly 25 to 30 %
larger, which on a 1 MB index costs more than the 69 KB the decompressor
weighs.

## What the lite build contains

`--no-default-features` on wasm32 drops candle, gemm, tokenizers, regex,
fancy-regex, rayon and rand. What is left: `SAED` container parsing and
brotli decompression, BM25, the learned-sparse arm with a pure-Rust WordPiece
query tokenizer (`src/wordpiece.rs`, verified id-for-id against the
`tokenizers` crate on 208 queries), weighted RRF fusion, page grouping,
snippets, QA ranking, sidecar attachment and the JSON surface. The dense arm
works when the worker hands `search()` a query vector (WebGPU lane); without
one it is reported in `degraded` exactly as before.

`capabilities()` returns `{"dense_wasm": false, "sparse": true, "version": ...}`
so the worker knows to fetch `eddie-dense.wasm` only when a visitor consents
to a `wasm-candle` lane.
